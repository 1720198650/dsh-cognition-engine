## 二、备忘说对的部分（采纳为改进项）

### 1. 一句话定位准确
> 「差异化不在记得多，在作废有依据」

### 2. 去重缺中间态（完全正确）

现状——`playbook.submit()` 一刀切：

```ts
if (similarity >= 0.70) return { accepted: false, reason: '重复' }
```

0.70–0.85 之间没有「让人看一眼」的选项。

**改进方案（半天，立刻有用）**：

```
hash 完全相同        → 直接拒
相似度 ≥ 0.85        → 自动合并（旧内容进 history）
0.70 ≤ 相似 < 0.85   → 进「疑似重复」待确认，不丢弃
```

### 3. 审计缺分析（部分正确）

备忘说「可写不可读」是**错的**——已有 `audit.tail()` + HTTP 路由 + 界面「查看最近审计」按钮。

但它说「缺过滤、分析」是对的。**改进（两小时）**：按 `op` 聚合计数，而不是只列原始 20 行。

### 4. 「Recency ≠ truth」（veritas-tms 立场）

反思结论**不能因为「新」就覆盖旧准则**。我们碰巧没踩（候选走独立审核，不走 supersedes），但要明确写进设计原则。

## 四、P0–P5 提案的处置

**核心判断：它给你开了五层治理，而你刚删掉 753 行过度结构。**

用更多结构解决「结构没被用起来」的问题，是同一类诱惑。

| 提案 | 判断 | 理由 |
|---|---|---|
| **P0 evidenceGrade + warrant** | ❌ 现在做等于白做 | 5 条准则全是用户亲手确认 → 全是 `corroborated` → 字段值整齐划一 → 零行为差异 |
| **P1 utilitySignal** | ❌ 反向有害 | 5 条准则按任务类型过滤，很可能把唯一相关的那条滤掉 |
| **P2 影子队列** | ⏸ 方向对，时机早 | 现在没有候选积压，没有瓶颈要解 |
| **P3 axioms** | ❌ 过度设计 | 3–5 条公理用 `pinned: true` 布尔字段就够 |
| **P4 反思引擎三层解耦** | ❌ 问题已解决 | 反思产出进候选队列，编辑权在用户 |

### 备忘漏掉的最大风险

**注入占比。** 现在 5 条准则已占满 600 字符预算，还有 1 条被截断。准则涨到 20 条时没有任何自适应机制——只会静默截掉低分的。这比「证据等级」迫切得多。

## 五、当前真实瓶颈：反馈回路是断的

```
准则 5 条 · helpfulTotal 2 · harmfulTotal 1
```

这两个数是手动打的假值。**真实使用反馈为 0。**

任何「证据等级 / 效用信号 / 影子验证」都需要数据运转。现在加治理层，等于给没有车流的路口装红绿灯。

## 六、「让插件慢慢学习」——可行路径

### 6.1 先厘清「学习」在这里是什么

**模型权重不会变。** 所有「学习」都发生在**上下文**里：

> 学习 = 该浮现的东西浮现，该沉下去的东西沉下去。

所以「学习」不是模型变聪明了，而是**外部记忆承担了学习的职责**。这正是 SCL 的核心分离：

> 模型提出（proposes），外部记忆保存已验证状态（preserves verified state）。

### 6.2 三层学习能力，我们各做到哪

| 层次 | 含义 | 现状 |
|---|---|---|
| **技能学习** | 学会可复用的做法 | ✅ 准则本雏形（蒸馏→候选→人工确认） |
| **纠错学习** | 同一个错不犯第二次 | ✅ `supersedes` + `harmful` 计数 + 有效期 |
| **条件化学习** | 知道同一招在什么场景下用 | ⚠️ 主题层给了骨架，但注入不分场景（全量注入） |
| **像人一样学习** | 形成直觉、举一反三、类比迁移 | ❌ 做不到。需要权重更新或大量结构化数据 |

**诚实的边界：我们能做「技能的积累与淘汰」，做不到「变得更有悟性」。**

### 6.3 真正的断点：反馈闭环

「慢慢学习」的瓶颈不是缺学习机制，而是**缺反馈**。现在的循环是断的：

```
模型使用准则 → 没有人记录用得对不对 → 蒸馏时模型自己判断哪些有用（自己评自己）
```

**最短路径不是 P0–P5，是「隐式反馈」**：

#### 设计：用户纠正即信号

1. **记录每轮注入了哪些准则**（已在 `buildInjectedContext` 里有数据，只需存一份快照）
2. **下一轮用户否定/纠正时**，把上一轮注入的准则记 `harmful +1`
3. **用户确认执行正确时**（关键词："对"、"就是这样"、"继续"）记 `helpful +1`
4. 累计 `harmful ≥ 3 且 > helpful` → 自动退场（机制已有）

**为什么这个方案好**：
- 零新增数据结构（复用 `helpful`/`harmful`）
- 零额外 token
- 捕捉的是**真实使用结果**，不是模型自评
- 对应 veritas-tms 的「确信度」，只是确信度来自实际使用而非引用次数

**风险**：
- 关键词判定会有误报（用户说"不对，但这条准则本身是对的"）
- 缓解：只在**明确否定句**时降级，且一次只降 1 分，需 3 次才退场

### 6.4 第二个可选机制：条件化注入（P1 的正确形态）

备忘的 P1 用「任务类型」过滤，5 条准则时是负收益。

**正确形态**：不是过滤，而是**分组后让模型自己选**——这个 v0.10.0 已经做了（按主题分组 + 自查要求）。

真正缺的是：**当准则数超过预算时，优先注入哪些**。
现在按 `helpful - harmful*2` 排序，但这两个数没人打 → 等于随机。
**接上隐式反馈后，这个排序才有意义**。

### 6.5 哲学项目各借一层（按顺序）

| 顺序 | 借什么 | 来自 | 落在哪 |
|---|---|---|---|
| 1 | **已验证 / 未验证** 的区分 | SCL | 隐式反馈的 helpful 就是"验证通过" |
| 2 | **Recency ≠ truth** | veritas-tms | 蒸馏产出的新候选不能自动覆盖旧准则（已有） |
| 3 | **主题相关 ≠ 效用相关** | ITEM | 注入排序应该按「在类似任务里被用过且有用」，不是「和当前话题像」 |
| 4 | **公理门控** | HADES | 用 `pinned` 字段标记不可淘汰的准则，而不是新文件 |
| 5 | **规范与工具解耦** | GRACE | 已有：模型生成候选，代码合并，用户裁决 |
