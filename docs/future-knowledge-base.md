# 暂缓方案：AI 知识库（接线 + 持久化）

> **状态：不做，但保留思路。**
> 记录时间：2026-11-03
> 相关调研：[topic-research.md](topic-research.md)（论文篇）、[topic-research-oss.md](topic-research-oss.md)（开源项目篇）

---

## 一、这是什么

调研过程中产生的一个念头：如果把「记忆 → 主题图」这条链路真正**接线 + 持久化**，
它可能演变成一个本地 **AI 知识库**：

```
大量文档/笔记 → 抽取 → 聚类成主题 → 主题摘要 → 全局问答
```

这确实是个真实需求，但**它不是现在这个插件的目标**。

---

## 二、为什么现在不做

### 2.1 目标不同

| | 当前插件 | AI 知识库 |
|---|---|---|
| 输入 | 跨会话的零散约定（几十~几百条） | 大量文档（千~百万级） |
| 目标 | **精确取少量事实** | **从海量内容里找全局答案** |
| 规模 | 总共几千 token | 装不进上下文，必须压缩 |
| 关键能力 | 时间语义、失效、注入 | 分块、向量、聚类、摘要 |

**当前插件不需要压缩，知识库必须压缩**——这是两种相反的设计目标。

### 2.2 技术底座不同

我们删掉的那套（`assimilate` / `accommodate` / `communities` / PPR）
建立在**字头二元组余弦**上——零依赖换来的代价是相似度质量差。

知识库场景下这个底座根本不够用：
- 需要**真正的向量模型**（本地 embedding 或 API）
- 需要 **LLM 实体/关系抽取**（GraphRAG 路线）
- 需要**增量索引**与**社区重建策略**

**结论：重新写比复活旧代码便宜。**

### 2.3 留着代码的代价

死代码会：
- 误导后来的判断（"我们有图记忆能力"）
- 增加维护面（改动记忆结构要同步改它）
- 掩盖真问题（"主题为 0"这件事被代码存在感掩盖了几个月）

## 三、将来真要做的触发条件

满足**任意两条**再考虑：

- [ ] 单工作区记忆长期 **> 2000 条**（全量进上下文不再可行）
- [ ] 出现**跨文档问答**需求（"把这 30 份文档整理里的问题汇总一下"）
- [ ] 已引入**向量能力**（本地 embedding 模型，或接受 API 调用）
- [ ] 已有**文档分块 + 增量索引**需求（不只是记录对话）

## 四、那时应该怎么做（技术选型备忘）

### 4.1 不要复用什么

- ❌ 现在的字面相似度聚类（`graph.ts`，已删除）
- ❌ 在线 label propagation（Graphiti 重建会删旧社区，不稳定）
- ❌ 每条写入都跑聚类

### 4.2 应该抄什么

| 需求 | 抄谁 | 做法 |
|---|---|---|
| 文档 → 知识图谱 | **GraphRAG** / **Cognee** | LLM 抽取实体关系，Leiden 聚类，LLM 社区报告 |
| 增量索引 | **Cognee** | 增量 cognify，不平铺重建 |
| 社区检索通道 | **Graphiti** | BM25 + 向量 + RRF 混合，社区作为第四通道 |
| 人工主题容器 | **Cognee NodeSets** / **Memobase** | 标签作为 first-class 节点，可过滤 |
| 全局摘要 | **Cognee Global Context Index** | root + bucket 的预置上下文 |

### 4.3 已知的坑（来自调研）

- GraphRAG 构造成本极高（GraphRAG-Bench 实测 **7993 万 tokens** 建一个索引）
- 社区全局检索**伤害细节型 QA**（RAG vs GraphRAG 统一评测：NQ 上纯向量 64.78 > Graph Local 63.01）
- 实体抽取出错会被图拓扑放大（噪声放大效应）
- 增量更新会导致社区结构重构

### 4.4 数据规模参考

```
300 条 × 50–100 tokens ≈ 15,000–30,000 tokens   → 全量进上下文，不需要结构
```

**在到达 10⁴ token 量级之前，任何"结构化压缩"都是净损失。**

## 五、和当前方案的关系

当前方案（B）把「主题」做成**人定的适用范围键**：

```
记忆 —— 发生过什么
准则 —— 应该怎么做
主题 —— 适用于哪类任务
```

这套数据结构（`topics.json` + `topicIds`）**恰好是将来知识库的种子**：
主题注册表可以扩展成知识库的分类维度，不需要推倒重来。

**所以：现在做的 B，本身就是给未来留的接口。**
