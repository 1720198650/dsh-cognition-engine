# 学习笔记：腾讯混元 Hy-Memory（2026-11-16）

来源：<https://github.com/Tencent-Hunyuan/Hy-Memory/blob/main/README.zh.md>（Apache-2.0，2067★，152 fork，
Python，最近推送 2026-11-15）。论文三篇：EMNLP 2026（双系统认知记忆）、CMB 编码记忆基准（ICLR 2027 投稿）、
Hy-Memory-30B-A3B 归因强化学习写入模型（arXiv:2610.22196）。

**一句话**：这是我们要做的事的**工业级、重依赖版本**。它把"记忆分层 + 夜间巩固 + 冲突消解 + 经验复用"
全做齐了，而且有论文和 30B 专用模型。我们的插件在"记忆广度"这个维度上不可能赢，只能换维度。

---

## 一、它的架构（值得逐条对照）

### 1. Chat：8 层认知结构

| 层 | 内容 | 对我们的意义 |
|---|---|---|
| L0 BASIC_INFO | 基础信息 | — |
| L1 RAW | 原始对话，**append-only** | 和我们的事件流同构 |
| L2 FACT | 原子事实，**版本化、不可变记录** | 和我们的双时态同构；它也是"不可变 + 版本" |
| L3 SUMMARY | 会话摘要 | 我们的 wiki 想做的就是这个 |
| L4/L5 | 保留位 | 说明他们也承认"层不是越多越好" |
| L6 SCHEMA | 心智模型（抽象叙事模板，图层） | 我们的"主题"更弱，值得看 |
| L7 INTENTION | 前瞻意图，**带有效期，过期转普通事实** | **可直接借**：我们有"待办"但没有"会过期的意图" |

### 2. 三档处理模式（本质是成本分级）

| 模式 | 做什么 | 图库 | 我们的对应 |
|---|---|---|---|
| `lite` | 只 embedding 写入 + 检索，**不调 LLM** | 否 | 我们没有这档，等于每条都要跑判定 |
| `pro` | + LLM 抽取 + **reconcile 冲突处理** | 可选 | 我们的 `supersede` + 判定 ≈ 这块 |
| `ultra` | + **System 2 图式归纳 + 跨域 sweeper，`evolve()` 触发** | 是 | 我们的 `dreaming` 是它的简化版 |

**"ultra 每晚自动整理"这条，和我们 dreaming 的思路完全一致**——但它是夜间批处理，我们是手动触发。
这是我们可以马上改的一点：把 dreaming 挂到定时任务上。

### 3. Working：双层记忆（事实 + 经验）

| 层 | 记什么 | 每次会话 | 门槛 |
|---|---|---|---|
| 事实层 `WorkingFact` | 做了什么：任务/做法/结果 | **恰好 1 条，不设门槛** | 无 |
| 经验层 `Experience` | 下次能复用的做法 | **0–N 条** | **必须过价值门槛** |

经验层字段：`task / search_keys / solution / boundary_envs / confidence`。
两层双向链接（`fact.derived_experience_ids` ↔ `experience.source_fact_ids`），
旧事实保留 `superseded` 状态，用 `fact_chain_summary` 回溯演化过程。

**这条最该抄进我们的准则本**：
- 我们现在的准则候选没有 `boundary_envs`（适用边界），也没 `confidence`；
- 它的"事实必记、经验过门槛"正好对应我们"记忆不设门槛、准则要人批"。

### 4. Coding：版本演进链（diff 链）

关键设计是**「装饰器而不是检索器」**：
> 向量层决定返回哪几条事实；演进链只负责在每条事实下面**挂上它所涉及代码的全部改动版本**。

理由很硬：事实抽取刻意不粘贴代码（预算留给坐标），所以被撤掉的那版代码不在事实里，
事后也读不回来——只能零 LLM 地把每版真实 diff 存下来。

**这条对我们最有启发**：我们一直在纠结"要不要把东西塞进检索"。
它的答案是——**不塞检索，挂在结果上**。这和我们的"偏置不产出文本、只在阈值后面起作用"是同一种设计哲学。

## 二、必须承认的差距（不粉饰）

| 维度 | Hy-Memory | 我们 |
|---|---|---|
| 工程规模 | monorepo + SDK + 桌面端 MemHub + CLI，多语言界面，152 fork | 单插件，3000 行 |
| 依赖 | ChromaDB / Kuzu / Qdrant / Neo4j / SQLite / PostgreSQL | **零依赖，纯 JSON** |
| 模型 | 自研 30B-A3B 记忆写入模型（RL 训练） | 复用人宿主模型 |
| 验证 | EMNLP 2026 + 自建基准 CMB | 只有一个 0.5 天原型 + 1 条真实事件 |
| 场景 | chat / working / coding 三链路 | 单链路 |

**结论：在"长期记忆"这个赛道上，正面竞争没有意义。** 它 2067 星、有论文、有专用模型。

## 三、可借的四条（都不违反零依赖）

1. **意图带有效期**（L7）：`INTENTION` 过期自动转普通事实。
   我们可以给 `manage_long_task` 的 pending 项加 `expiresAt`，过期下沉为普通记忆，而不是永远挂着。
2. **经验层有边界与置信度**：准则候选补 `boundary_envs`（什么情况下不适用）和 `confidence`。
   这直接解决我们"准则被滥用"的老问题——**没有边界的准则等于口号**。
3. **事实必记、经验过门槛**：明确写进方案——记忆不设准入，准则必须过闸门。
4. **装饰器而非检索器**：凡"补充信息"，一律挂在结果上，不塞进检索索引。
   wiki 就这么做：**wiki 不参与检索排序，只在命中事实后作为附注展示。**

## 四、不借的三条

1. **多后端依赖**：Chroma/Qdrant/Neo4j —— 直接违反我们"零依赖纯 JSON"的硬约束。
2. **图数据库式图式归纳（ultra sweeper）**：我们要的"主题"只需一层，不需要图投影与关系路径。
3. **自研写入模型**：不可行，也不必要。

## 五、差异化的结论（更新）

它能赢的：记忆广度、跨应用汇聚、编码链路、多后端。
**我们能赢的只有一处：可验证性。**

- 它的事件流同样 append-only，但我没在 README 里看到哈希链或可校验的链完整证明；
- 它的 `superseded` 是状态标记，不是结构性不可逆；
- 它的"经验"没有"我因为哪条翻案而改变"的可追溯账本。

所以我们该做的不是"更好的记忆"，而是**"能证明自己没被改过、且改变可追溯到具体事件"的那一层**——
给任何记忆系统做体检，包括给 Hy-Memory 做。

|---|---|---|---|

按它的经验**这个顺序是错的**——wiki 应该挂在事实后面。
