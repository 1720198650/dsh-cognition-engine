## 一、一句话定位

> 别的插件让 AI 记住经验；
> **我们让 AI 知道经验什么时候该作废。**

## 二、为什么要做，以及不做什么

### 2.1 问题

反思引擎现在没有沉淀：

```
调用 cognition_reflect → 输出三段分析 → 对话结束 → 分析消失
```

一次性消费，下次会话不记得，模型也不会因此变聪明。

### 2.2 竞争分析（必须先看）

| 插件 | 星 | 它做什么 |
|---|---|---|
| [dsh-host-rsi](https://github.com/pk14742952-AD/dsh-host-rsi) | ★38 | 自动观察会话 → 沉淀「可信教训」→ 相似任务自动注入；L1/L2/L3 三级信号加权；148 测试 |
| [dsh-dream](https://github.com/STARDUSTLC666/dsh-dream) | ★11 | 任务结束整理候选经验 → 核对适用范围/条件/例外 → 人工采纳 → 回用 |

**「记忆 → 准则 → 注入」这条链路已经不新颖。** 如果照做，是重复造一个更简陋的轮子。

### 2.3 所以我们只做他们没做的

两家共同的空白：**准则写入即永久，没有时间语义**。

而真实约定会过期：

```
「本周先用 A 方案」       → 下周失效
「这个项目阶段别动 B」     → 阶段结束解除
「等 X 上线后改回 Y」     → X 上线即触发
```

这正好是我们双时态的主场。

| 能力 | rsi | dream | 我们 |
|---|---|---|---|
| 经验沉淀 | ✅ 自动观察 | ✅ 任务复盘 | ✅ 记忆蒸馏 |
| 自动注入 | ✅ | ✅ | ✅ |
| 人工审核 | — | ✅ 更细 | ✅ |
| **准则有效期** | ❌ | ❌ | **✅** |
| **准则冲突检测** | ❌ | ❌ | **✅** |
| **可追溯双时态记忆** | 部分 | 部分 | **✅** |

### 2.4 明确不做

| 不做 | 理由 |
|---|---|
| 自动观察会话 | 需要宿主事件流，rsi 已做得更好 |
| 全量注入准则本 | DC 的做法，准则本一大就爆 |
| 整篇重写准则本 | 两篇论文实证会崩（见 3.3） |
| 纯自评入库 | 错误会成簇扩散（DC） |

## 三、三篇核心论文的结论

### 3.1 三篇的共同点与分歧

| 维度 | ACE (ICLR 2026) | Dynamic Cheatsheet | Reflexion |
|---|---|---|---|
| 结构 | bullet 列表，带 id 与 helpful/harmful 计数 | 分节 + `<memory_item>` + `Count` | 纯文本 1–3 条滑窗 |
| 更新 | **LLM 只产 ADD，合并去重由确定性代码做** | 整篇重写 | 追加后滑窗截断 |
| 检索 | 全量进 system prompt | 全量（DC-RS 只检索给 curator） | 全量 |
| 权重信号 | helpful / harmful 双向计数 | Count 单向计数 | 无 |

### 3.2 最重要的结论：LLM 只提议，代码做合并

ACE 的 Curator 提示词里**只有 ADD 一种操作**，merge / dedup / 计数全部是
「lightweight, non-LLM logic」。

**这是 delta 比 rewrite 高 13.4 个点的根因**，也是成本降 82% 的根因。

> 我原方案让 LLM 输出 `add / revise / retire` 三种操作——**这条要改**。
> LLM 只提候选，操作由代码决定。

### 3.3 context collapse 的实证数字

DC 在 AppWorld 上全量重写的实际轨迹：

```
第 60 步   18,282 tokens   准确率 66.7%
下一步        122 tokens   准确率 57.1%   ← 比不 adapt 的 63.7% 还低
```

**整篇重写不是"效果差一点"，是会塌到比基线更差。**

### 3.4 噪声准则比没有准则更差

ACE 的实验：每轮都注入有害反射 → **66.7，低于基线 70.7**。
每 5 轮注入一次 → 76.1。

**结论：坏条目的伤害大于好条目的收益。审核不是可选项。**

### 3.5 brevity bias 的具体形态

ACE 记录的实际退化结果：迭代若干轮后，提示收敛成

> "Create unit tests to ensure methods behave as expected"

——正确、空洞、无信息量。

### 3.6 DC-∅ 对照：必须减掉基线

DC 的消融表里有一列「空小抄」（同指令、不给任何经验）：

| 任务 | 原始 | 空小抄 | 最佳 |
|---|---|---|---|
| AIME24 (Claude) | 23.3 | **36.7** | 50.0 |
| 等式配平 (GPT-4o) | 50.0 | **88.0** | 100 |

**光换指令格式就涨 13–38 个点。** 所以：

> **每条准则必须携带「只有这个用户/这个项目才知道」的信息。**
> 判定问法：这条换成任何项目都成立吗？成立就不该写。

### 3.7 Mem0 的量化收益

| 指标 | Mem0 | 全上下文 |
|---|---|---|
| p95 延迟 | 1.44 s | 17.1 s（−92%） |
| token 占用 | 7 k | 26 k（−73%） |

## 四、准则本设计

### 4.1 数据结构

借鉴 ACE 的 bullet 形式 + DC 的 Count + 我们的双时态：

```jsonc
// cognition-playbook.json
{
  "version": 1,
  "revision": 7,
  "updatedAt": 1793700000000,
  "entries": [
    {
      "id": "ctxt-00001",
      "section": "约定",              // 约定 | 坑 | 状态 | 未分类
      "content": "发版流程五步，不跳步；纯文档改动不升版本号",
      "helpful": 2,                  // ACE 式双向计数
      "harmful": 0,
      "sourceIds": ["mem-7-249d46"],
      "validFrom": 1793600000000,    // 我们的差异化：何时生效
      "validTo": null,               // null = 长期有效
      "status": "active",            // active | retired | expired
      "createdAt": 1793700000000,
      "updatedAt": 1793700000000,
      "note": ""
    }
  ]
}
```

**双向计数**比单向 `hits` 好：`helpful=5 harmful=3` 和 `helpful=8 harmful=0` 是两种不同的条目，
前者该复核，后者该保留。

### 4.2 条目写作约束

| 约束 | 判据 |
|---|---|
| 必须携带私有信息 | 换成任何项目都成立 → 不写（DC-∅ 推论） |
| 必须是可执行指令 | 读它能不能改变下一步动作 |
| 12–80 字 | 太长挤占预算 |
| 不写具体数据 | 版本号、文件数、路径属于记忆，不属于准则 |

### 4.3 渲染格式

```
[ctxt-00001] helpful=2 harmful=0 :: 发版流程五步，不跳步；纯文档改动不升版本号
```

模型可以点名引用 `[ctxt-00001]`，我们就能回写计数。这是 ACE 的做法，比纯自然语言好——
**条目可被引用，才可能被统计**。

分组渲染：

```markdown
## 工作约定
- [ctxt-00001] helpful=2 harmful=0 :: 发版流程五步，不跳步；纯文档改动不升版本号
- [ctxt-00004] helpful=0 harmful=0 :: HTTP 接口一律 POST + 查询字符串

## 已知的坑
- [ctxt-00002] helpful=5 harmful=0 :: 改 JS 一律用 Node 脚本，PowerShell 会吃掉模板字符串
```

**不渲染 `validTo`、来源、id 以外的元数据**——省 token。

### 4.4 预算

| 项 | 值 | 依据 |
|---|---|---|
| 总字符 | ≤ 600 | 当前 digest 实测 190 字符 / 133 token；600 字符 ≈ 400 token |
| 条目数 | ≤ 12 | 600 / 平均 40 字 |
| 单 section | ≤ 5 条 | 防止某类挤占 |
| 截断排序 | `helpful − harmful×2`，同分按新近 | 坏条目优先淘汰 |

**每个 section 至少保留 1 条**（否则某类信息会被完全挤掉）。

### 4.5 与 digest 的关系

```
有 active 条目  → 只注入准则本
无 active 条目  → 回退 buildCoreDigest
```

**绝不叠加。**

## 五、生成管线

### 5.1 三个角色（照 ACE）

| 角色 | 输入 | 输出 |
|---|---|---|
| **Generator** | 任务/问题 | 不使用；我们不是解题场景 |
| **Reflector** | 记忆集 + 当前准则本 + 未覆盖的记忆 | 固定 5 字段 JSON |
| **Curator** | 反思结果 + 当前准则本 | **只产 ADD 候选** |

### 5.2 Reflector 的固定输出

```jsonc
{
  "reasoning": "…",
  "error_identification": "…",
  "root_cause_analysis": "…",
  "correct_approach": "…",
  "key_insight": "…",
  "marks": [ { "id": "ctxt-00002", "mark": "helpful" } ]
}
```

`marks` 用于给现有条目打 helpful/harmful，实现 ACE 式的信用分配。

### 5.3 Curator 只产候选

```jsonc
{
  "reasoning": "…",
  "candidates": [
    { "section": "坑", "content": "…", "sourceIds": ["mem-16-…"] }
  ]
}
```

提示词里必须写死：

- **"Do NOT regenerate the entire playbook"**（ACE 原文）
- 只输出候选，不要输出改删指令
- 每条必须给出 `sourceIds`

### 5.4 确定性合并（不调 LLM）

LLM 输出候选之后，**以下全部由代码做**：

```
1. 语义去重：与现有 active 条目余弦 ≥ 0.90 → 丢弃候选并标记「与 ctxt-xxxxx 重复」
   （ACE 实测 90% 最佳；50%/70% 都不如它）
2. 长度校验：12–80 字，超长截断、过短丢弃
3. section 校验：不在枚举内 → 未分类
4. 来源校验：sourceIds 必须存在，全部无效 → 丢弃
5. 私有性启发式：与所有现有条目 + 常见套话库比对，命中套话 → 丢弃并记录
6. 入库：status = pending，等人工审核
```

**为什么不用 LLM 决定改删**：ACE 的公开提示词只有 ADD，改删靠剪枝；
DC 的整篇重写会崩。**让 LLM 做减法是不可靠的。**

### 5.5 淘汰（代码做）

触发条件（任一）：

| 条件 | 动作 |
|---|---|
| `harmful ≥ 3` 且 `harmful > helpful` | retire |
| 连续 90 天 `helpful = 0` | retire 候选（进审核队列） |
| 所有 `sourceIds` 已 superseded 且过期 | expire |
| 总数超 12 | 按 `helpful − harmful×2` 淘汰最低 |

**retire 不删除**，`status = retired`，历史可查。

### 5.6 反思轮数与频率（照 ACE 超参）

- 反思轮数上限 **5**（3–5 最优，10 会变差）
- batch = 1
- 新条目**每 5 轮**才注入一次评估，不是每轮（噪声反射比没有更差）

## 六、时间语义（我们的差异化核心）

### 6.1 条目为什么要有效期

| 场景 | 无有效期 | 有有效期 |
|---|---|---|
| 「本周先用 A」 | 下周还在注入 | 自动过期，不再干扰 |
| 「这个阶段别动 B」 | 阶段结束后仍在生效 | 阶段结束即解除 |
| 「等 X 上线改回 Y」 | 永远不会自动切回 | 到点触发复核 |

### 6.2 生成时怎么判断

Reflector 的提示词加一条硬要求：

> 如果这条准则只在特定阶段/时间有效，必须在 `validUntil` 里给出 ISO 时间或相对表达
> （如 `"7d"`、`"2026-12-31"`）；不确定就留空表示长期有效。

**宁可留空，也不要乱猜。**

### 6.3 过期处理

- `validTo` 已过 → `status = expired`，**不再注入**
- 设置页提示「3 条准则已过期，要复核吗」
- 复核后可以延长 `validTo` 或 retire

### 6.4 冲突检测

新条目入库前，与现有 active 条目做冲突检测（复用图式的 `classifyEdge`）：

- 同 section + 内容互斥 → 不自动合并，**两条都进审核队列**，界面标注「疑似冲突」
- 审核时人看到两个并排，决定留哪个

**不自动裁决**——自动裁决就是另一种"整篇重写"。

## 十三、往回看：我们已经引用了，但没吃透的思想

做 v2 时回头审了一遍 README 的「参考与致谢」和自己的代码，发现三类遗漏。

### 13.1 自己的代码里，已建未用

| 能力 | 状态 | 说明 |
|---|---|---|
| `reinforce()` / `activation` | **完全没接线** | 只在 `memory.ts` 内部出现，无外部调用；`activation` 永远是 0 |
| `communities()` | 算得出，没人用 | 连通分量社区聚类，只在 `graph.ts` 内部 |
| `representatives()` | 算得出，没人用 | RAPTOR 式「代表样本」，只在 `graph.ts` 内部 |

**`reinforce` 的后果最严重**：`autoArchive()` 里 `fact.activation > maxActivation` 恒为真，
所以**归档实际上只看时间，不看使用**。

### 13.2 最重要的遗漏：准则本就是 MemGPT 的 Core Memory

我们引用 MemGPT 时写的是「记忆分层与分页（对照参考）」——**只当参考，没落地**。

MemGPT 的三层：

| 层 | MemGPT | 我们对应 |
|---|---|---|
| **Core Memory** | 常驻上下文、模型可自我编辑 | **准则本（就是这个）** |
| Recall Memory | 近期对话 | 会话内记忆 |
| Archival Memory | 长期存储、检索进入 | `cognition-state.json` 的记忆库 |

**这个映射给准则本一个正统的理论位置**，也解释了它为什么该：

- 常驻（每轮都注入）
- 短（600 字符上限）
- 由模型自我维护（**MemGPT 的核心机制是 function call 自我编辑 core memory**）

**落地**：给模型一个 `cognition_playbook` 工具，让它能主动提议修改准则（进待审队列，不直接生效）。
这才是 MemGPT 的灵魂，比我们原来的「设置页手动编辑」更进一步。

### 13.3 第二重要的遗漏：准则本让图式有了产物

CAM 的构造主义是「观察 → 图式 → 超图摘要」，我们只做到第二层：

```
记忆  →  图式（主题聚类）  →  ？？？
          ↑
     只用于召回，不产出任何东西
```

**准则本正好填上第三层**：

```
记忆  →  图式  →  准则本
```

意义有两层：

1. 理论上完整了（三层抽象）
2. **解决了「主题对用户有什么用」这个老问题**——之前实测主题价值有限，
   因为它是只读的中间产物；现在它有了下游消费者。

### 13.4 其他值得吸收的小点

| 来源 | 思想 | 用在哪 |
|---|---|---|
| LongMemory / memoripy | 不可变版本 + 完整历史 | **准则条目 revise 时保留旧版本**（`history[]`），不原地覆盖 |
| A-MEM | 卡片盒动态链接 | 准则间可建 `related: [id]`，审核时提示「这是一组」 |
| RAPTOR | 逐层摘要 | 准则分两层：抽象原则 + 具体做法，只注入原则（解预算紧张） |
| DC | `memory_item` 有 `<description>` + `<example>` | 审核界面用 `representatives()` 挂一条原文例证 |
| GraphRAG | 社区摘要 | `communities()` 可给 section 分组建议（价值低，暂不做） |

### 13.5 采纳决定

| 想法 | 价值 | 成本 | 决定 |
|---|---|---|---|
| MemGPT 的 core memory 定位 + 自我编辑工具 | 高 | 低 | **采纳，进 P2** |
| 图式 → 准则本（三层抽象） | 高 | 中 | **采纳，写作文档的定位章节** |
| 准则条目版本链 | 中 | 低 | **采纳，进 P1** |
| `representatives()` 做审核例证 | 中 | 低 | **采纳，进 P2** |
| RAPTOR 分层注入 | 中 | 中 | 暂缓，P3 后按预算压力评估 |
| 准则间链接 | 低 | 低 | 暂缓 |
| `communities()` 分组建议 | 低 | 低 | 不做，或直接删掉该能力 |

### 13.6 对实施计划的修订

原 P0–P4 不变，但每阶段增加：

| 阶段 | 新增内容 |
|---|---|
| P0 | ✅ 已完成（2026-11-03）：衰减计入 activation、噪声命中不加权、强化落盘 |
| P1 | 准则条目加 `history[]`（版本链） |
| P2 | 新增 `cognition_playbook` 工具（模型自我编辑，进待审队列）；审核界面挂 `representatives()` 例证 |
| P3 | 无变化 |
| P4 | 文档补「三层抽象」定位说明 |
