# 冻结权重的 LLM Agent 如何靠外部记忆"学习"

> 调研时间：2026-11-04。所有数字取自论文原文/官方摘要；查不到的写"未找到"。
> 面向目标：零依赖、本地 JSON、几十到几百条记忆、已有双时态+准则本+反思的插件。

## 0. 结论先行（五条能直接搬的机制）

| # | 机制 | 出处 | 为什么适合我们 |
|---|---|---|---|
| 1 | **bullet + helpful/harmful 计数器 + delta 增量合并** | ACE (2510.04618) | 和"准则本"结构几乎一一对应；计数器由 Generator 自报"这条有用/误导"来填，正好补上断掉的回路 |
| 2 | **按次准入：preserve / abstract / ignore** | PATH-Bench 的 SEU (2608.01149) | 不改变记忆库，只在"用的时候"过滤，最便宜的抗负迁移手段 |
| 3 | **先让模型说出"它理解的任务"，用户纠正理解而不是答案** | MemPrompt (2201.06009) | 直接回答"是准则错了还是模型理解错了"：把理解显式化就能分开 |
| 4 | **行为规则必须写成祈使句并锚定在决策点** | forge_dc (NeurIPS 2026 PALM) | 同样的纠正，写成规则 95% 遵守，写成描述性检索文本只有 55% |
| 5 | **保留分 = exp(−n/S)，S 由效用+频次决定，且只降可达性不删除** | Oblivion (2604.00131) | 可作为超容量时的淘汰函数；但几十条规模下不建议默认开启衰减 |

一句话总结方向：**这个领域已经从"存什么"转向"什么时候取、取来怎么用、用完怎么记功过"**。我们的痛点恰好卡在第三件事上。

## 1. 经验学习类

### 1.1 ExpeL（AAAI 2024）— insight 的格式与计数器
- **核心机制**：ReAct + Reflexion 在训练任务上反复试错，把轨迹存进 experience pool；然后做两种对比提取 insight：①同一任务的"失败轨迹 vs 成功轨迹"配对；②L 条成功轨迹成组。LLM 对已有 insight 列表执行四种操作：**ADD / EDIT / UPVOTE / DOWNVOTE**。新 insight 初始重要度计数 = 2；UPVOTE 或 EDIT +1；DOWNVOTE −1；**降到 0 就删除**。
- **insight 存成什么**：就是一段自然语言祈使句列表，无结构、无向量、无分类，例如"找不到物品时，考虑物品的性质和典型用途，而不是只按房间搜索"。推理时**整份 insight 列表拼进任务说明**，另外用 Faiss + all-mpnet 检索 top-k 成功轨迹当 few-shot。
- **关键数字**：HotpotQA 39%（Reflexion 三轮 40%）；ALFWorld 59%（Reflexion 54%），且不需要重试；只用 insight / 只用检索：HotpotQA 36% / 31%，ALFWorld 50% / 55%（任务类型决定哪种更强）。把 reflection 也塞进 insight 提取反而更差（反思会带幻觉）。
- **链接**：https://arxiv.org/abs/2308.10144
- **对插件**：计数器的**更新来源是"新证据对比"**，不是"使用后反馈"——这正是我们缺的那一半。另外它证明了几十条 insight 全量注入是可行的。

### 1.2 Voyager（2023）— 技能库的验证/检索/组合
- **核心机制**：技能 = 可执行代码，key 是 GPT-3.5 生成的描述嵌入，value 是代码本身。**只有通过验证才入库**：执行程序拿到环境反馈和执行错误 → 连同 GPT-4 自省 critic 的判断一起回灌 → 最多 4 轮，自验证确认任务完成才 commit；4 轮不过就换任务。检索用"计划 + 环境反馈"的嵌入取 **top-5** 技能；新技能可直接调用旧技能，实现组合。
- **关键数字**：3.3× 独特物品、2.3× 移动距离、木质层级快 15.3×、石 8.5×、铁 6.4×，唯一解锁钻石层；160 轮迭代发现 63 种物品；**top-5 检索准确率 96.5%（309 个样本）**；去掉自验证模块，发现物品数 −73%。
- **链接**：https://arxiv.org/abs/2305.16291
- **对插件**：可迁移的是"**先验证再入库**"这条纪律，而不是嵌入检索。我们的"验证"可以是：这条准则是否真的在某个任务上导致了好结果（有证据链）才允许进核心区。

### 1.3 Agent Workflow Memory（AWM，2024）— 工作流怎么归纳
- **核心机制**：workflow = 一句自然语言描述 d + 步骤序列；每个步骤 = 环境状态的自然语言描述 + 推理 + 可执行动作。归纳靠 prompt：让 LM 从多条任务轨迹里找**重复出现的子过程**，要求"每条 workflow 至少两步，把具体值抽象成变量（如 `{product-name}`）"。可以离线（从标注样例）或在线（从自判成功的测试轨迹）。
- **关键数字**：WebArena 相对 +51.1%，Mind2Web 相对 +24.6%；WebArena 上滚动几十个样例后比基线高 22.5 个点，前 40 个样例提升最快；每样例归纳出 7.3–7.4 条 workflow，**使用率 0.94（WebArena）/0.91（Mind2Web）**，workflow 间功能重叠仅 0.08。文本格式 vs 代码格式几乎无差（元素准确率 +0.6、步骤成功率 +0.3、任务成功率 −1.2）；规则式归纳 vs LM 归纳只差 0.1。
- **链接**：https://arxiv.org/abs/2409.07429
- **对插件**：workflow 的"描述+步骤+变量占位"格式可直接借用；但**自动归纳需要多条同域轨迹**，几十条记忆的规模下，手工/半自动（用户触发"把这次做法存成准则"）比自动归纳划算。注意 AWM 在负迁移历史下会退化（见 2.2）。

### 1.4 Reflexion（NeurIPS 2023）— 失败后怎么回写
- **核心机制**：失败后让模型用自然语言写"为什么失败、下次怎么改"，存进长期记忆；下一次尝试把**最近 3 条反思**拼进 prompt。不训练、不检索、不分主题。
- **关键数字**：HumanEval pass@1 91%（GPT-4 80%）；AlfWorld +22%、HotPotQA +20%、HumanEval +11%；记忆只保留最近 3 条经验。
- **链接**：https://arxiv.org/abs/2303.11366
- **对插件**：最便宜的冷启动——反思文本直接进上下文。但它是**任务内**学习，跨任务不迁移（ExpeL 明确指出这点）。所以反思必须有一个"晋升成准则"的出口，否则永远在同一个任务里打转。

### 1.5 ReasoningBank（ICLR 2026）— 结构化记忆条目 + 噪声容忍
- **核心机制**：每条记忆 `{title, description, content}`；对每条轨迹最多抽 3 条；top-k 检索**默认 k=1**；检索结果拼进 system prompt，并附一句"每一步请先明确说明你是否要使用某条记忆，再行动"。成功轨迹抽"为什么成功"，失败轨迹抽"教训与规避策略"。
- **关键数字**：相对提升最高 20%，交互步数少 16%；某设置下 token 只多 4.3%、性能 +20.5%；**只用成功轨迹 46.5 → 加入失败轨迹 49.7**；LLM-as-judge 判对率仅 72.7%，但把判官准确率从 100% 模拟降到 50%，70%–90% 区间性能基本不掉。
- **链接**：https://arxiv.org/abs/2509.25140
- **对插件**：两条直接可用的结论——①**k=1 就够**，不需要复杂检索；②**反馈信号不要求准**，70% 准确率的判官也能用。这大幅降低"自动反馈"的工程门槛。

### 1.6 ACE（ICLR 2026）— 最贴近"准则本"的架构
- **核心机制**：上下文 = 一组结构化 bullet，每条 bullet 有 **metadata（唯一 id + 记录被标记 helpful/harmful 次数的计数器）** 和 content（一条可复用策略/领域概念/失败模式）。流程：Generator 解题并**标出哪些 bullet 有用、哪些误导** → Reflector 提炼教训 → Curator 产出**增量 delta**（只写新增/修改的 bullet）→ 用非 LLM 的确定性逻辑合并、去重。原则叫 grow-and-refine：只追加与就地更新，绝不整篇重写。
- **关键数字**：agent 任务平均 +10.6%，金融 +8.6%；AppWorld 上仅靠执行反馈、无标注 +17.1%；离线设置比 ReAct+ICL 高 12.3%、比 GEPA 高 11.9%；在线设置比 Dynamic Cheatsheet 高 7.6%；无 GT 在线 +14.8%；**上下文坍缩实例：60 步时 18,282 token / 66.7 分 → 下一步被重写成 122 token / 57.1 分（低于不 adapt 的 63.7）**；去掉 delta 增量更新，TGC −11.7%、SGC −27.8%；适配延迟 −86.9%。对噪声反思有容忍，只有持续对抗性污染才会跌破基线。
- **链接**：https://arxiv.org/abs/2510.04618
- **对插件**：这就是"准则本"的论文版。**计数器不该由人填，而该由每次使用时模型自报"这条帮了/误导了"+ 结果好坏来填**；更新必须是增量的，不要每次让模型重写整个准则文件。

### 1.7 其他 2025–2026 自改进 agent
- **Self-Improvements in Modern Agentic Systems: A Survey**（2026-07，97 页）：把 agent 拆成"基础模型 + 脚手架（prompt / memory / tools / control logic）"，把自改进形式化为"自诱导更新算子"，按**更新目标**和**驱动信号**分类。适合当索引读。
  https://arxiv.org/abs/2607.13104
- **MemHarness**（2026-07）：反对"把检索到的经验原样回放"，主张在每一步**按当前状态重构**经验再给模型；用 GRPO 端到端训练。思路可借（"重构而非回放"），但训练部分我们做不了。
  https://arxiv.org/abs/2607.28272
- **Mem0**（2025-04，工程系统）：从对话里动态**抽取—巩固—检索**长期记忆；LOCOMO 上 LLM-as-judge 相对 OpenAI memory 提升 26%，p95 延迟低 91%，token 省 90%+，图记忆再高约 2%。它的"巩固"阶段就是 LLM 决定改写/合并/作废旧条目，可当作"记忆维护"的工程参考（但我们规模小，用确定性规则即可）。
  https://arxiv.org/abs/2504.19413

## 2. 终身学习 / 遗忘

### 2.1 Lifelong Learning of LLM-based Agents: A Roadmap（IEEE TPAMI）
- **核心机制**：把 agent 拆成感知 / 记忆 / 行动三模块；记忆分**四类：工作记忆（prompt、工作区、用户上下文）、情景记忆（过往经验、数据回放/特征回放、continual RL、自我经验）、语义记忆（外部知识、知识图谱/文档的持续学习）、参数记忆（训练/微调进权重的知识）**。
- **稳定性-可塑性**：survey 主要在**参数层面**讨论 catastrophic forgetting 与 loss of plasticity 的两难；对外部记忆，它给出的是评测口径而非机制。原文的评测三视角：整体准确率、历史任务稳定性、未来任务可塑性；指标 AP、AIP、FGT、BWT、FWT，其中
  `FGT_t = 1/(t−1) Σ_{i<t} [max_{j∈{i..t}} J_{j,i} − J_{t,i}]`，
  `BWT_t = 1/(t−1) Σ_{i<t} (J_{t,i} − J_{i,i})`。
- **链接**：https://arxiv.org/abs/2501.07278
- **注意**：**"外部记忆上的稳定性-可塑性"这篇没有正面展开**，真正做这件事的是下面的 2604.27003。

### 2.2 PATH-Bench（2026-08）— 迁移与遗忘怎么量
- **核心机制**：用多模型 one-shot ICL 的收益矩阵估计任务间的有向关系，据此构造"探针任务 + 正/负迁移历史"的序列；探针反复出现，读它的轨迹算指标。50 条序列 × 5 次运行；正迁移预热 5 个任务，中间队列 100 个任务，探针间隔 6–12 个任务，70% 来自主导迁移集。
- **指标公式**（n 为探针出现次数，p_cold 为冷启动、p_warm 为预热后）：
  - `FWT = 1/(n−2) Σ_{i=3..n} (p_i − p_cold)`
  - `BWT = 1/(n−2) Σ_{i=3..n} max(0, p_i − p_warm)`
  - `FGT = 1/(n−2) Σ_{i=3..n} max(0, p_warm − p_i)`
  即 BWT 与 FGT 是把"相对预热基准的偏差"拆成正负两半。
- **表结构**（Table 1）：行 = 8 个 agent；列 = `Positive Dominant{AP, FWT, BWT, FGT}` + `Negative Dominant{AP, FWT, BWT, FGT}`；两个数据集（BigCodeBench 单轮代码生成、WildToolBench 多轮工具调用）；AP 为 %，FWT/BWT/FGT 为百分点（pp）。无记忆基线 = DeepSeek-V4-Flash，AP 70.18 / 67.67。
- **关键发现**：①迁移强 ≠  retention 强（HippoRAG-v2 负迁移下 FWT 7.03pp 但 FGT 16.15pp）；②**近期经验主导**——agent 的探针状态更多反映"最近一段历史"而非累计历史；③负迁移历史下，AWM、两个 RAG、SimpleMem 会下降，BGE-M3 RAG 掉 14.7pp；④他们的 SEU 方案在**使用时**逐条判断：可直接复用→preserve，只可迁移高层模式→abstract，否则 ignore。FGT 最多降 16.84pp（HippoRAG-v2）和 13.07pp（AWM），WildToolBench 上 0.50–3.76pp。
- **链接**：https://arxiv.org/abs/2608.01149
- **对插件**：SEU 的三分类是**成本最低的抗干扰手段**：不动记忆库，只在注入前加一次判断。另外"近期主导"意味着检索排序里 recency 权重应高于累计计数。

### 2.3 Oblivion（EMNLP 2026）— decay-driven activation 的具体公式
- **核心机制**：把遗忘定义为"可达性下降"而非删除。读路径决定何时查记忆（不确定性 + 保留分门控），写路径决定强化哪条。三层记忆：动态程序性 L1 / 语义 L2 / 抢先情景 L3。
- **公式**：
  `R_t(c) = exp( − n_t(c) / S_t(c) )`，
  `S_t(c) = ( U_t(c) + F_t(c) + ε ) · T`
  其中 n_t(c) 是距上次访问经过的**交互轮数**（不是墙钟时间），U 是效用代理 ∈[0,1]，F 是访问频率代理 ∈[0,1]，ε 防除零，T 是衰减温度（越大衰减越慢）。高 utility / 高频的簇衰减慢；未被强化的簇 R 下降 → 检索排序靠后、可能被逐出缓冲区，但**永不从库里删除**，未来可被重新激活。
- **关键数字**：120K 交互跨度下 token 成本最多降 73%；GPT-4.1-mini 在 2K 设置 6.29→8.41、32K 6.05→6.79；最小的 Phi-4-mini 在 32K 从 1.33→3.36。温度消融 T∈{1,3,5,10,20,50}：T=1 保留率趋近 0；**T=10 最优**；T=50 缓冲区饱和，退化成 always-on 检索。规则类记忆（`memory_type="rule"`）受保护，永不被删。
- **链接**：https://arxiv.org/abs/2604.00131
- **对插件**：公式简单可移植。但注意它是为 120K 级历史设计的；**几十到几百条记忆时，衰减基本没有收益，反而会误伤低频但重要的准则**。建议只在"超出容量上限"时用 R 做淘汰排序。

### 2.4 "记忆反而让 agent 变差"的证据群
- **How Memory Management Impacts LLM Agents**（2025-05）：提出 **experience-following**（输入相似 → 输出也高度相似），由此产生两个病：**error propagation**（检索到坏记录 → 复读并放大 → 再写回 → 继续传播）和 **misaligned experience replay**（相似但本质不匹配的记录拖累当前任务）。对策：选择性写入 + 组合删除（按近期检索频次删冗余、按历史任务效用删低质/过时）；**比 naive memory growth 平均高 10 个百分点**；add-all 会导致自我退化；周期性删除只掉 <2%。
  https://arxiv.org/abs/2505.16067
- **When Continual Learning Moves to Memory**（2026-04）：冻结权重下，稳定性-可塑性**在记忆层重现**——上下文窗口有限，新旧经验在检索时竞争。用 (k,v) 框架拆"表示"与"组织"两轴。**抽象的程序性 insight 比原始轨迹更可靠**；原始轨迹在同任务内是资产、跨任务时是负债；负迁移集中打击最难的样本。BabyAI A→B：Cond-Ind 前向迁移 +15.0% 但 BWT −10%（遗忘），Cond-Step 前向 −2.5% 却 BWT +3%——**强前向迁移与严重遗忘可以同时出现**。另一个细节：Cond-Ind 下 88.5% 的查询都检索到同一条 top-1，检索覆盖率仅 5.4%。
  https://arxiv.org/abs/2604.27003
- **Dynamic Cheatsheet 的反例**（2025-04）：GPT-4o 在 AIME 2024 上基线 20.0%，**把全部历史原样拼进上下文后掉到 6.7%**，而策展记忆是 40.0%。"全都塞进去"比不塞更差。
  https://arxiv.org/abs/2504.07952
- **MemHarness**（2026-07）：把检索到的经验当静态记录原样回放，是负迁移的主因；主张按当前状态重构。
  https://arxiv.org/abs/2607.28272

## 3. 上下文工程 / 提示层学习

### 3.1 "写进系统提示" vs "检索进上下文"：没有找到严格头对头实验
明确说：**未找到**一篇把"同一批学习成果分别写成系统提示 / 只做检索"做严格对照的论文。但有四组间接证据，方向一致：

| 证据 | 对照 | 结果 |
|---|---|---|
| ExpeL | insight 全量驻留 vs 只检索成功轨迹（few-shot） | 知识型任务（HotpotQA）insight 36% vs 检索 31%；动作型任务（ALFWorld）50% vs 55%。**任务类型决定通道** |
| forge_dc | 同一纠正写成祈使 RULE 注入决策点 vs 作为描述性文本检索进上下文 | 合规率 **95% vs 55%**，且 RULE 方案每查询 token 少约 10× |
| Dynamic Cheatsheet | 策展记忆 vs 全历史直拼 vs 只检索不策展 | Claude AIME 2024：50.0% vs 26.7%；GPQA：DC-RS 68.7% vs 纯检索 63.6%。**策展 > 检索 > 全量直拼** |
| ACE | 离线写系统提示 vs 在线写记忆 | 两种都有效（平均 +10.6%），但**形式**（bullet + 增量）比通道更决定成败 |

**可下的结论（我的综合，不是某篇原文）**：决定效果的第一变量是**形式**——短、祈使、带触发条件、锚定在决策点；第二变量才是**通道**。行为规则放常驻系统提示；案例/过程放检索；两者都要，但别混成一大段散文。

### 3.2 Dynamic Cheatsheet 之后的新工作
- **ACE**（见 1.6）：把"cheatsheet"升级成带计数器的 playbook，并解决 context collapse。
- **ReasoningBank**（见 1.5）：把 cheatsheet 条目结构化为 {title, description, content}，显式用失败轨迹。
- **SEU / PATH-Bench**（见 2.2）：在"用"的环节做准入。
- **forge_dc / Decision Context**（NeurIPS 2026 PALM workshop）：从人类纠正 + 自评的工具调用失败中提取行为信号，编译成祈使 RULE，注入到"该规则生效的决策点"。DC-Bench 71 个场景 / 9 个行为维度；**95% 合规 vs 朴素检索 55%**；"Only Rules Rule"——同一条纠正在会话内被应用过，但换成无锚定的描述性文本后经常被忽略。
  https://openreview.net/forum?id=7XhMLOsQoA
- **MemHarness**（见 2.4）。

### 3.3 ICL 到底学到了什么（2025–2026）
- **Is In-Context Learning Learning?**（ICLR 2026，Adrian de Wynter）：ICL 在数学形式上满足"学习"的定义，但大规模消融（记忆化、预训练、分布漂移、提示风格与措辞）后发现：**示例越多，准确率对示例分布、模型、提示风格、输入语言特征越不敏感**；模型是从 prompt 的规律性里"演绎"模式，导致分布敏感性（CoT 尤甚）。结论：自回归的 ad-hoc 编码不是稳健的学习机制，通用泛化有限。
  https://mlanthology.org/iclr/2026/dewynter2026iclr-incontext/
- **Large Language Models Cannot Self-Correct Reasoning Yet**（ICLR 2024）：没有外部反馈时，模型对推理的自我纠错不仅不可靠，**有时还会让性能下降**。
  https://arxiv.org/abs/2310.01798
- **对插件的含义**：不要指望"把准则写进 prompt"让模型学会新能力；记忆提供的是**证据与模式**，能力仍在权重里。因此反馈信号必须来自**外部结果**（工具、测试、用户），不能只靠模型复读自己的推理。

## 4. 反馈信号获取

### 4.1 显式纠正
- **MemPrompt**（EMNLP 2022）：记忆是 `误解的问题 → 用户澄清` 的键值对；检索相似问题，把对应澄清拼进 prompt；用相似度阈值做门控。**关键设计：让模型先输出"它对用户意图的理解 u"，用户纠正 u 而不是纠正答案**——用户不需要知道正确答案也能给反馈。
  数字：两个伦理任务上相对提升均 **>25%**；检索到的反馈 **97%** 情况下有效，约 3% 无正面作用；在某类错误里 **30% 来自坏检索**、18% 来自检索失败。
  https://arxiv.org/abs/2201.06009
- **forge_dc**（见 3.2）：纠正要**编译成祈使规则**并锚定决策点，才有 95% 的遵守率。

### 4.2 自评 / 代理信号（没有用户时）
- **ReasoningBank**：LLM-as-judge 判轨迹成败，判官本身只有 **72.7%** 准确率，但模拟 50%–100% 判官准确率后发现 **70%–90% 区间性能几乎不变** → 噪声可容忍。
- **ACE**：Generator 每次解题时**逐条标注哪些 bullet 有用/误导**，这就是计数器的一手来源。
- **DC**：Curator 在**没有 ground truth** 的情况下自判"这个解法是否值得存"，并决定增/改/删。
- **AWM**：在线模式用 LM evaluator 给轨迹打二值成功标签，只有判成功才归纳 workflow。
- 共同点：**判的是"结果/轨迹"，不是"推理步骤"**。这与 3.3 的"不能自我纠错推理"并不矛盾。

### 4.3 隐式反馈（用户没说"不对"）
**未找到**专门研究"agent 从隐式用户反应中学习"的论文。可用的弱信号（工程推断，非论文结论）：用户重述同一请求、用户改写了输出、用户中途打断、同一问题反复出现、用户手动改了文件/参数、会话被放弃。
处理原则：**弱信号不直接改计数**，只做"待确认"标记；同一模式出现 ≥2 次才升级为一次负反馈。

### 4.4 用"用户纠正"作为记忆降级的系统
- **forge_dc**：纠正 → 规则（不是降级，是重写形式）。
- **MemPrompt**：纠正 → 新记忆条目（不降级旧条目）。
- **ACE**：负反馈 → 计数器 −1，且可由 metadata 过滤"被标为有害"的 bullet。
- **ExpeL**：DOWNVOTE → 计数 −1，到 0 删除。
- **未找到**把"用户纠正"直接当作某条记忆降级信号、并做因果归因的专门论文——这块是空白，正好是我们能做出的差异化。

### 4.5 【重点】用户说"不对"时，怎么判断是准则错了还是模型理解错了

先说结论：**不要在这一步让模型猜。用"理解显式化 + 使用日志 + 合规检查"三件事把它变成可判定的问题。**

**第一步：把"理解"和"执行"分开记录（事前）**
- 每次回答前，让模型用一行说出它的理解：`我理解你要的是：……`（MemPrompt 的 u）。
- 让模型标注它用了哪几条准则：`[应用: pb_012, pb_007]`（ReasoningBank 的显式声明 / ACE 的 bullet 标记）。
- 这两行是后面归因的唯一依据；没有它们，任何"降级"都是瞎猜。

**第二步：用户说"不对"时，先做一次二选一澄清（事中）**
> "你是说 (a) 我理解错了你的要求，还是 (b) 理解对了但做法/规则不对？"

MemPrompt 的核心洞察就是：**用户纠正"理解"比纠正"答案"容易得多**，不需要他知道正确答案。一次二选一的成本远低于一次错误的降级。

**第三步：按四象限归因（事后）**

| 理解是否匹配 | 准则是否被应用 | 判定 | 动作 |
|---|---|---|---|
| 不匹配 | — | **检索/范围问题**，不是准则错 | 不改计数；收窄该条的 trigger/topic；检查是不是它把任务"框"错了 |
| 匹配 | 应用了，且输出违反准则文字 | **执行问题**（指令遵从） | 不改计数；把准则改写成祈使句、前移位置、加"当……时"锚点（forge_dc） |
| 匹配 | 应用了，且输出符合准则但结果差 | **准则错/过宽/过时** | harmful +1，强制挂证据链；累计 ≥2 次独立纠正才降级 |
| 匹配 | 没应用 | **检索没召回 或 该用没用** | 记 retrieval_miss；补 trigger 词；不降级 |

**第四步：对有争议的条目做一次反事实重放（只在必要时）**
同一任务跑两遍：带该条 / 去掉该条，其他不变。**只有"去掉后结果变好"才算该条的因果负作用**。这正是 ExpeL"成功 vs 失败轨迹对比"的推理逻辑，只是用在单条上。几十条记忆的规模下，一周做几次完全付得起。

**为什么不能只看"结果差"就降级**：memory 研究里的 error propagation 表明，坏结果会被写回并放大（2505.16067）；同时 MemPrompt 显示 30% 的错误其实来自坏检索。**把检索错误记到准则头上，会让准则本越用越保守、最后全是废话。**

**准则"错"还要再分四类**，动作不同：
1. 事实错（环境变了）→ 改文本，保留旧版本（双时态 valid_to）。
2. 范围过宽 → 加条件，不降级。
3. 过时 → 设 valid_to，转冷存储。
4. 与另一条冲突 → 不删，加优先级/适用条件。

## 5. 哪些做法在几十条记忆的规模上仍然有效

先算一笔账：一条中文准则约 30–60 token。**200 条 ≈ 6k–12k token**。这在 32k 上下文里占 20%–40%，在 128k 里可接受。所以规模问题的本质不是"存不下"，而是"全量注入会稀释注意力、且无法区分新旧"。

### 5.1 直接有效（可照搬）
| 做法 | 出处 | 小规模下的理由 |
|---|---|---|
| 准则全量拼进 prompt | ExpeL | 原文就是全量 concat；几十到一两百条完全放得下 |
| 每条记忆 `{title, description, content}` | ReasoningBank | 结构小、可读、可人工审 |
| **k=1 检索** | ReasoningBank | 几十条时 top-1 已足够；k 大反而引入干扰 |
| 使用时三分类准入 preserve/abstract/ignore | PATH-Bench SEU | 只在注入前加一次判断，不改库 |
| bullet + helpful/harmful 计数 + 增量 delta | ACE | 与准则本同构；避免整篇重写导致"越改越短" |
| 规则写成祈使句、锚定决策点 | forge_dc | 与规模无关，纯形式收益（95% vs 55%） |
| 抽象 insight 优于原始轨迹 | 2604.27003 | 小样本下原始轨迹的跨任务污染更致命 |
| 选择性写入 + 按效用删除 | 2505.16067 | 平均 +10pp，add-all 会自我退化 |
| 最近 3 条反思驻留 | Reflexion | 极便宜，适合冷启动 |
| recency 优先于累计计数 | PATH-Bench | "近期历史主导"是可复现的实证 |

### 5.2 不要照搬（大规模实验的产物）
| 做法 | 为什么不适合我们 |
|---|---|
| 向量库 / 嵌入检索（Voyager、ExpeL 的 Faiss） | 几十条用标签+关键词+recency 就够；嵌入还带来 top-1 坍缩（2604.27003 里 88.5% 查询命中同一条） |
| 时间/轮次衰减（Oblivion） | 为 120K 跨度设计；几十条时衰减会误伤低频重要准则。只在超容量时当 LRU 用 |
| 自动归纳 workflow（AWM） | 需要多条同域轨迹；小规模下归纳成本 > 收益，改为"用户触发晋升" |
| 端到端训练（MemHarness 的 GRPO、SEAL 类） | 冻结权重前提，直接排除 |
| 分层多级记忆（L1/L2/L3） | 几百条不需要三层；两层（常驻核心 / 检索池）足够 |
| 让弱模型自动策展（DC 的教训） | GPT-4o-mini 上 DC 出现负收益；小模型 curation 会污染记忆 |
| 全历史直拼 | GPT-4o AIME 20.0% → 6.7%，比不拼更差 |

### 5.3 给这个插件的具体参数建议
- **两层注入**：常驻核心 20–40 条（按效用排序，≈2k–3k token）+ 每轮检索 3–5 条。
- **检索**：topic 标签 → 关键词 → recency 三级排序；同一 topic 最多取 1 条，强制多样性。
- **容量**：上限 300 条；到上限先淘汰 `status=probation` 且 90 天未用的。
- **计数先验**：Beta(1,1)；`helpful/(helpful+harmful)` 低于 0.3 且样本 ≥5 才降级；单次纠正永不直接删除。
- **晋升**：反思 → 候选准则（probation）→ 至少 2 次成功证据 → active。对应 Voyager 的"验证后入库"。
- **成本**：归一因（4.5 第三步）每次约 1 次额外调用；SEU 准入只在"检索条数 >3 或置信度低"时调用。

## 6. 获取反馈信号的具体可行做法

### 6.1 信号源按可靠性排序
1. **工具/测试/退出码**（最硬）：编译失败、测试红、命令非零退出——零成本、无歧义。代理每次工具调用都该记一条。
2. **用户显式纠正**（最贵但最有信息量）：不只是一句"不对"，而是"不对 + 他实际想要什么"。
3. **用户隐式反应**（弱）：重问、改写、打断、放弃、手动改——只标记待确认。
4. **模型自评**（最便宜、最脏）：判结果不判推理；70% 准确率可用（ReasoningBank）。

### 6.2 把"计数"拆成三个字段
现在的 `helpful/harmful` 是结果，缺少"是否被应用"。建议：
```
applied        // 模型自报"我用了这条"的次数
applied_good   // 用了且结果好
applied_bad    // 用了且结果差
missed         // 该用没用（检索未召回 / 召回了没用）
user_corrected // 用户明确纠正且归因到这条的次数
```
`helpful/harmful` 由 `applied_good / applied_bad` 派生，**且每次变化必须挂一条 evidence（trace_id / 用户原话）**——这与"准则带写死的证据链"天然吻合：没有证据，不允许改计数。

### 6.3 数据结构建议（在现有 JSON 上加字段）
```json
{
  "id": "pb_012",
  "text": "用户说'整理一下'时，先问清是排版整理还是内容精简，再动手。",
  "form": "imperative",
  "trigger": ["整理", "梳理", "归拢"],
  "topics": ["文档"],
  "status": "active",
  "stats": {"applied": 12, "applied_good": 9, "applied_bad": 3,
            "missed": 1, "user_corrected": 1},
  "evidence": [
    {"trace": "t_20261103_04", "type": "success", "at": 1793000000000},
    {"trace": "t_20261104_11", "type": "user_correction",
     "quote": "不是让你删内容", "at": 1793100000000}
  ],
  "valid_from": 1792000000000,
  "valid_to": null,
  "last_used": 1793100000000
}
```

### 6.4 让回路真正闭合的三个钩子
1. **每次注入后**：模型必须在回答里带一行 `[应用: pb_012]`（ReasoningBank 做法），解析后 `applied += 1`。
2. **每次工具结果后**：非零退出/测试失败 → 如果本条被应用，则 `applied_bad += 1`，否则 `missed += 1`。
3. **每次用户说"不对"后**：走 4.5 的二选一 → 四象限 → 只有落在"准则错"象限才 `user_corrected += 1`。

### 6.5 为什么这套在噪声下也能工作
- ReasoningBank：判官 72.7% 准确率，70%–90% 区间性能不敏感。
- ACE：反思有噪声也能用，只有持续对抗污染才跌破基线。
- ExpeL：新 insight 起始计数 2、可被 UPVOTE/DOWNVOTE 往返，本身就是抗噪设计。
- memstudy：选择性写入 + 删除比 add-all 高 10pp——**宁可少记，不要乱记**。
